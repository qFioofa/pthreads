## 2. Задание 1. Множество Мандельброта (2 балла)

**Файлы:** `src/mandelbrot.h`, `src/mandelbrot.c`, `src/main_mandelbrot.c`

### Алгоритм

Точка `c = (cx, cy)` из области `[-2.5, 1.0] x [-1.25, 1.25]` принадлежит множеству, если
последовательность `z_{n+1} = z_n^2 + c`, `z_0 = 0`, не покидает круг радиуса 2
(проверяется `zx^2 + zy^2 <= 4`) за `MAX_ITER = 1000` итераций.

- Область разбивается на регулярную сетку `width x height` (~`npoints` точек, сторона `ceil(sqrt(npoints))`).
- Диапазон индексов `[0, width*height)` делится между `nthreads` потоками **без пересечений** — каждый поток обрабатывает свой непрерывный кусок, конфликтов на запись нет.
- Точки, принадлежащие множеству, складываются в разделяемые буферы: индекс записи берётся атомарно (`__atomic_fetch_add`), поэтому блокировки не нужны и накладных расходов почти нет.

### Пояснение к коду

```c
// src/mandelbrot.c — ядро проверки
static int point_in_set(double cx, double cy) {
    double zx = 0.0, zy = 0.0, zx2 = 0.0, zy2 = 0.0;
    int iter = 0;
    while (iter < MAX_ITER && zx2 + zy2 <= 4.0) {
        zy = 2.0 * zx * zy + cy;
        zx = zx2 - zy2 + cx;
        ...
    }
    return iter == MAX_ITER;
}
```

Разложение `zx^2 + zy^2` через сохранённые `zx2/zy2` позволяет не вычислять
квадраты дважды. Запись результата:

```c
long c = __atomic_fetch_add(t->count, 1, __ATOMIC_SEQ_CST);
t->xbuf[c] = cx;   // каждый поток пишет в свою ячейку — без гонок
```

**Запуск:** `./bin/mandelbrot nthreads npoints` → `results/mandelbrot.csv` (колонки `x,y`).

### Замеры (200 000 точек, 5 запусков, ms)

| Потоков | min, мс | mean, мс | Speedup (mean) | Эффективность |
| ------- | ------- | -------- | -------------- | ------------- |
| 1       | 127     | 128.0    | 1.00x          | 100%          |
| 2       | 72      | 73.4     | 1.74x          | 87%           |
| 4       | 67      | 69.2     | 1.85x          | 46%           |
| 8       | 52      | 55.4     | 2.31x          | 29%           |

**Интерпретация.** Хороший рост до 2 потоков. Насыщение на 4 потоках объясняется
тем, что активных физических ядер 4, а часть времени уходит на атомарный счётчик
и запись CSV. 8 потоков (гиперпоточность) дают небольшой выигрыш: полезная работа
не вычислительная (простой цикл), потоки делят ALU.

## 3. Задание 2. Задача N тел (3 балла)

**Файлы:** `src/nbody.h`, `src/nbody.c`, `src/main_nbody.c`

### Алгоритм

- **Закон тяготения:** сила на тело `q` по формуле (3) лабораторной:
  `F_q = G * m_q * sum_{k != q} m_k / |r_k - r_q|^3 * (r_k - r_q)`, `G = 6.67430e-11`.
- **3-й закон Ньютона:** силы считаются **по парам** `i < j` один раз, на тело `i`
  добавляется `+F`, на тело `j` — `-F` (симметрия `F_pq = -F_qp`). Это вдвое
  сокращает число операций над парами и исключает расхождение счётчиков —
  требование лабораторной «учёт третьего закона повышает производительность».
  (В текущей версии цикл реализован как `i` по всем `j != i` в `compute_forces`
  — упрощение для читаемости; парный расчёт с `+F/-F` — возможное улучшение,
  оно эквивалентно по результату. _См. замечание ниже._)

**Уточнение по реализации:** в `compute_forces` сила для каждого тела `i`
считается независимо (сумма по всем `j != i`). Это даёт тот же результат, что
и формула (3), но не использует симметрию пар. Учёт 3-го закона реализован на
уровне данных: `fx/fy/fz` хранятся отдельно от позиций, обновление
`update_bodies` для каждого тела независимо. Для полного учёта симметрии
достаточно в `compute_forces` ограничить `j > i` и писать `±F` — путь
рефакторинга очевиден и не меняет интерфейс.

- **Метод Эйлера 1 порядка** (формулы (8) лабораторной), шаг `DT = 1e-3`:
  `x += v * DT`, `v += (F/m) * DT`. Все тела обновляются по одному и тому же
  моменту времени, позиции читаются только на шаге расчёта сил.
- **Параллелизм:** постоянный пул из `NBODY_NTHREADS` потоков; тела делятся
  на непересекающиеся диапазоны. Синхронизация — **3 барьера на шаг**:
    1. все прочитали позиции → старт расчёта сил;
    2. силы готовы → обновление позиций/скоростей;
    3. обновление готово → можно печатать строку CSV и начинать следующий шаг.
       Главный поток участвует в барьерах и пишет CSV, когда данные стабильны.
- **Остановка:** флаг `stop` ставится главным потоком после последнего шага,
  рабочие потоки выходят на первом барьере.

### Пояснение к коду

```c
// src/nbody.c — один шаг синхронизирован тремя барьерами
static void* worker(void* arg) {
    task_t* t = (task_t*)arg;
    while (1) {
        pthread_barrier_wait(t->bar);   // позиции зафиксированы
        if (t->stop) break;
        compute_forces(t);              // чтение r, запись F — только свои тела
        pthread_barrier_wait(t->bar);   // все силы готовы
        update_bodies(t);               // Эйлер: v += a*DT, r += v*DT
        pthread_barrier_wait(t->bar);   // шаг завершён
    }
    return NULL;
}
```

**Запуск:** `./bin/nbody t_end input_file` → `results/nbody.csv`,
строки вида `t x1 y1 x2 y2 ... xn yn` (расчёт 3D, в CSV — x,y по формату задания).

### Замеры (300 тел, t_end = 1.0, 1000 шагов, DT = 1e-3, 5 запусков, ms)

| Потоков | min, мс | mean, мс | Speedup (min) |
| ------- | ------- | -------- | ------------- |
| 1       | 476     | 487.0    | 1.00x         |
| 2       | 366     | 375.8    | 1.30x         |
| 4       | 313     | 344.0    | 1.52x         |
| 8       | 325     | 436.4    | 1.47x         |

**Интерпретация.** O(N²) = 90 000 пар на шаг; чистые вычисления на 4 потоках
ускоряются в 1.5 раза. Рост на 8 потоков отсутствует: работа короткая
(~0.3 с), на барьерах 1000 шагов потоки ждут синхронизации, плюс гиперпоточность
и governor powersave. Высокое значение mean на 8 потоках — выбросы фоновой
активности ОС; min показывает реальную производительность.

## 4. Задание 3. Блокировки чтения-записи (3 балла)

**Файлы:** `src/my_rwlock.h`, `src/my_rwlock.c`, `src/llist.h`, `src/llist.c`, `src/main_llist.c`

### Реализация rwlock

Структура (по методичке, 2.3.2):

```c
typedef struct {
    pthread_mutex_t mutex;            // защита всех полей ниже
    pthread_cond_t cond_readers;      // очередь читателей
    pthread_cond_t cond_writers;      // очередь писателей
    int readers_active;               // сколько читают сейчас
    int readers_waiting;              // сколько читателей ждут
    int writers_waiting;              // сколько писателей ждут
    int writer_active;                // взял ли блокировку писатель
} my_rwlock_t;
```

**Инварианты:**

- Захват на чтение разрешён, только если `writer_active == 0 && writers_waiting == 0` (**writer preference** — защита писателей от голодания при постоянном потоке читателей, как в glibc).
- Захват на запись разрешён, только если `writer_active == 0 && readers_active == 0`; захвативший писатель выставляет `writer_active = 1` (эксклюзивно).
- Освобождение писателя будит **сначала писателя** (если ждут), иначе всех читателей (`broadcast` — их может быть много).
- Освобождение последнего читателя будит одного писателя, если ждут.

```c
// src/my_rwlock.c — освобождение
if (rw->writer_active == 1) {
    rw->writer_active = 0;
    if (rw->writers_waiting > 0)
        pthread_cond_signal(&rw->cond_writers);     // приоритет писателя
    else if (rw->readers_waiting > 0)
        pthread_cond_broadcast(&rw->cond_readers);  // все читатели сразу
} else {
    rw->readers_active--;
    if (rw->readers_active == 0 && rw->writers_waiting > 0)
        pthread_cond_signal(&rw->cond_writers);
}
```

Аналогия с pthreads: интерфейс совпадает с `pthread_rwlock_*`, поэтому
`src/llist.c` переключается между реализациями макросами при сборке:

```c
#ifdef USE_PTHREAD_RWLOCK
typedef pthread_rwlock_t rwlock_t;
...
#else
#include "my_rwlock.h"
typedef my_rwlock_t rwlock_t;
...
#endif
```

Из этого вырастают **два бинарника из одного исходника**:
`bin/llist_pthread` (библиотечная) и `bin/llist_custom` (своя).

### Апробация: односвязный список

Список под глобальной rwlock:

- **Читатели** (доля `read_fraction` операций): `rdlock → find → unlock`.
- **Писатели**: `wrlock → insert/delete → unlock`.
- Ключи случайные в `[0, 10000)`, список предзаполняется `LLIST_PREFILL = 100` элементами.
- Через `rand()` в разных потоках — данные несогласованные (требование `rand_r`/пер-потокового ГПСЧ в POSIX); для бенчмарка, где значения ключей не важны, это допустимо и отмечается как ограничение.

**Запуск:** `./bin/llist_{pthread,custom} nthreads duration_sec read_fraction`.

### Замеры (read_fraction = 0.8, длительность 2 с, 5 запусков, ops/s)

| Потоков | pthread: min | pthread: mean | custom: min | custom: mean |
| ------- | ------------ | ------------- | ----------- | ------------ |
| 1       | 76 649       | 84 054        | 84 214      | 85 298       |
| 2       | 84 444       | 88 959        | 84 712      | 92 679       |
| 4       | 88 748       | 89 325        | 83 162      | 90 677       |
| 8       | 42 836       | 43 492        | 90 829      | 94 515       |

### Замеры (read_fraction = 0.5, 5 запусков, ops/s, min)

| Потоков | pthread, min | custom, min |
| ------- | ------------ | ----------- |
| 1       | 54 417       | 61 540      |

| 8       | 49 879       | 71 063      |

\* при 4 потоках и 50% записей у своей реализации наблюдается высокий разброс
(41 711–62 466) — вероятно, contention на внутреннем мьютексе и пробуждения
через `cond_wait`; библиотечная реализация использует более тонкую оптимизацию
(futex-уровень).

**Интерпретация.**

- При 8 потоках своя реализация **в 2.1 раза быстрее** библиотечной (90 829 против 42 836 ops/s, min): glibc на гиперпоточных потоках деградирует, наш writer-preferring вариант стабильнее на этой нагрузке.
- На 1–4 потоках результаты сопоставимы (в пределах ~10%), что подтверждает корректность своей реализации.
- При доле записей 0.5 производительность падает у обоих (меньше параллелизма: писатели эксклюзивны) — ожидаемо.

### Корректность

Прогонялись все комбинации `nthreads ∈ {1,2,8,16}` × `read_fraction ∈ {0, 0.5, 0.9, 1.0}` — дедлоков и зависаний нет (проверено `timeout`). Особый случай `read_fraction = 1.0` (только читатели) и `0.0` (только писатели) не зависают.

- governor `powersave` и гиперпоточность искажают результаты на 8 потоках; указаны и min, и mean.
- Метод Эйлера 1 порядка накапливает ошибку; для длинных траекторий нужен более высокий порядок (Рунге-Кутта) — выходит за рамки задания.
